# 常見 SEO 情境（SEO Scenarios）

## 排名下降分析（Ranking Drop Analysis）

先給初學者一句話：
**先確認掉的是什麼，再猜為什麼掉。** 不要一看到流量下降就立刻大改網站。

### 第一步：確認問題的範圍
- 是所有頁面都下降，還是特定頁面？
- 是特定關鍵字下降，還是整體流量？
- 是自然搜尋流量下降，還是包含其他來源？

**工具：** GSC → 成效 → 比較日期範圍（下降前 vs 下降後）

### 常見原因排查

**1. Google 演算法更新**
- 先查 Search Console Data Anomalies，排除官方報表問題
- 再用 Google Search Status Dashboard 對照下降時間，不用未署名的 update 傳聞
- 撞上 Core Update 只代表「可能相關」；仍要分頁面、查詢、國家、裝置與站內改動
- Helpful content 已整合進核心系統，不再把它當獨立更新分支

Coach 要補的預期管理：
- Core Update 不是「處罰」
- 很多時候不是你突然做錯，而是 Google 重新比較後，覺得別的內容更值得排前面
- 在 update 還沒完全跑完前，不要急著全部砍掉重寫

**2. 技術問題**
- 網站有沒有突然無法存取？
- robots.txt 是否意外封鎖了重要頁面？
- HTTPS 憑證是否過期？
- 有沒有大規模的 404 錯誤？

**3. 內容被刪除或更改**
- 是否刪除了頁面？
- 是否更改了 URL 但沒有設重定向？
- 是否把 noindex 加到重要頁面？

**4. 競爭對手變強**
- 搜尋你的目標關鍵字，看是否有新的強競爭者出現

**5. 失去重要反向連結**
- Ahrefs Webmaster Tools → 查看最近丟失的連結

## 網站改版的 SEO（SEO for Web Redesigns）

### 改版前必做清單
1. **抓取現有網站** 用 Screaming Frog 存下所有 URL 清單
2. **記錄排名** 在 GSC 截圖或匯出目前的關鍵字排名
3. **記錄流量基準** 匯出目前的月流量數據
4. **識別重要頁面** 哪些頁面帶來最多流量？這些必須被保護

### 改版中必做
1. **保持 URL 結構**（盡量不改變），如果必須改 → 一定要設 301 重定向
2. **維持內容**（特別是帶來流量的頁面內容）
3. **保持所有 meta tag**
4. **避免在改版同時換主機**（兩個變數同時改，難以排查問題）

### 改版後必做
1. 用 Screaming Frog 重新爬取，確認重定向設定正確
2. GSC 提交新 sitemap
3. 監控 GSC 的爬取錯誤
4. 追蹤 1-4 週的排名和流量變化

## 新網站上線（SEO for New Web Launch）

### 上線前確認清單
- [ ] HTTPS 已設定
- [ ] robots.txt 已設定（且沒有封鎖 Google）
- [ ] sitemap.xml 已生成
- [ ] 每個頁面有獨立的 title 和 meta description
- [ ] H1 標籤在每頁設定
- [ ] 所有圖片有 alt text
- [ ] 內部連結結構正確
- [ ] 結構化資料設定（至少首頁的 Organization schema）
- [ ] GSC 已驗證網站
- [ ] sitemap 已提交到 GSC

### 上線後的 SEO 期待
新網站沒有官方固定的「Sandbox 3–6 個月」。時間取決於發現、爬取、索引、內容與競爭；用重要頁是否可索引、相關曝光是否開始出現來判斷，不用通用月份保證。

## 內容覆蓋要顧買家旅程前段，不能只守成交關

很多新站（B2B 尤其）敗在一個地方：只守著最後成交那一關。Gartner 調查，現在的買家約八成時間都在自己上網查，只有一成多真的在跟供應商接觸——等他來問你，心裡的名單早篩好了。很多網站的內容覆蓋剛好倒掛：最後一刻搜的品牌名、價格、購買頁都有排名，但他前面大半年搜的「怎麼選、常見錯誤、要注意什麼」幾乎一片空白。

同一個客戶不同階段搜的詞完全不一樣：剛意識到問題 → 搜痛點＋解法；認真考慮 → 搜規格、用法、注意事項；縮小名單 → 搜口碑、真實心得、有沒有人踩雷；最後才搜品牌名。名單在前三個階段就定型了。

做法：把現有關鍵字清單每個詞標上階段，算哪一段覆蓋率最低（通常是最前面兩段），先補那裡。但補完前段詞還不夠——網站內部要設計怎麼引導這些人往成交走（CRO），否則你辛苦把市場教育到一半，客人一轉頭選了早就在那裡等他的對手。好的 SEO 不只把詞鋪開，是讓來訪的人信任你、最終回頭下單。

## 新站為什麼贏不了老站：現任優勢與 quality test

新站客戶最常問：「AI 叫我做的 SEO 我全做了，為什麼還卡在第三頁？」要反問的是：你是把競品有的補齊了，還是給了 Google 一個**換掉現任**的理由？這兩件事差很遠。

Google 排名比的不是兩份從零開始的文件，是一個被驗證好幾年的老站 vs 一個沒有任何歷史的你。排第一的老站，Google 手上握著它多年的行為資料（多少人點、點完有沒有秒退、更新後穩不穩）——不代表它理論上最好，但證明了「已知可用」。你內容看起來一樣完整，這一格卻是空的。所以真正的問題不是「我有沒有跟對手一樣好」，是「Google 憑什麼把一個能用的結果，換成沒人驗證過的你」。現任本身就是一種優勢。

**Google 的測試（quality test）**：它偶爾會把你的新頁暫時抬上去、丟給真實使用者看反應（你的 CTR 有沒有比原頁好、有沒有人點完就跑回去改字重搜）。表現好，排名慢慢站穩；普通，就在前兩頁閃幾天又掉回去。被測試的訊號：頁面突然一波短期曝光、排名這幾天上竄下跳、同一頁開始出現在一堆相鄰查詢裡，有時某地區／裝置或長尾詞先動、核心大詞還沒醒，配上 Google 突然頻繁回來抓、曝光一路往上。

**這時最忌諱手癢**——排名一跳就改標題、動架構、砍段落，Google 正在收集的行為資料會被你一改全歸零、測試作廢。該做的是先凍結標題、主架構、核心答案，坐著看：哪些查詢被抬上去測、CTR 和點擊有沒有跟漲、測完哪些排名留下來。真要改就只改一個變數、記錄前後。別人工灌點擊，要累積的是自然查詢下的滿意度證據。

**怎麼真的取代老站**（新站競爭力分兩層：內容覆蓋 vs 歷史反應。補齊內容通常只做到第一層，第二層接近零）：
1. **挑基準頁——挑「頁面」不是「網域」。** 對一個目標詞，把前十名每個 URL 做小表：可追到的最早發布／版本時間、最近一次大改、覆蓋的搜尋意圖、必要屬性、原始證據。別用網域註冊日代替頁面歷史（十年老網域剛上線的 URL 可能沒累積；新網域裡長期更新的單頁也不能當零歷史）。能查就用 Wayback Machine、頁面上的發布／更新日期交叉比對，日期只是線索不是鐵證，查不到就標「未知」。選前十裡**最年輕、但已經能進結果**的頁當基準頁，先把語意、核心答案、必要實體、基本可信度做到對等——這一步只回答「我有沒有資格被比較」。
2. **補一個真正改變使用者決策的差異**，不是盲目加 FAQ、字數、實體。關鍵是使用者能不能很快看懂：這是誰的答案？解決什麼問題？哪些條件影響結果？例如搜「A vs B」，別先大篇幅講品牌背景、把比較表埋很深；一進去就把「哪個適合低預算、哪個支援某功能、什麼情況結論會反過來」講清楚，讓使用者少繞幾圈、少開一個分頁——這才可能帶來更好的後續行為訊號。換配色、加動畫、塞冷門實體都不算真差異。
3. **建 query map、集中一組窄而相近的查詢。** 新手別一開始想把大詞全拿下。為一支頁面列出核心詞、長尾限制詞、地區／用途／預算變體，還有讀完後自然會冒出的 next query，確認這頁能真正完成一組相鄰任務。上線後在 GSC 每週追同一批查詢（曝光、點擊、排名區間、CTR、進站後下一步、轉換）。初期把一小組相近需求做深，比十頁各打幾個詞累積回饋更快。

發稿前先自問三題：基準頁是哪一頁？額外價值讓使用者少做哪一步？你要在哪組 query 觀察什麼？答不出來，多寫幾千字也只是把答案拉長。（期待管理數據 → `45-benchmarks-and-timelines.md`）

## Google Core Update 後的恢復

### Core Update 的特點
- 次數與 rollout 時間不固定，以官方 dashboard 為準
- 更新時間重合不排除技術問題、需求變化或競爭者改善
- 系統會持續重評，不把「等下一次 Core Update」當成恢復條件

初學者白話版本：
- Core Update 比較像 Google 重新洗牌
- 不是說你犯規，而是它重新評估「誰更值得排前面」
- 所以恢復通常不是修一個小設定就立刻回來

### 如果你的網站被 Core Update 影響
1. **不要恐慌，不要立刻大規模修改**（讓 Update 完全推出後再評估）
2. 閱讀 Google 官方的「Self-assessment questions」（搜尋 "Google core update self-assessment"）
3. 對照問題逐一審查你的網站
4. 重點關注：E-E-A-T、內容品質、是否為人類寫作

可以這樣引導用戶：
- 先看是不是少數頁面掉，還是整站掉
- 再看掉的是不是原本就偏薄、偏舊、偏不明確的內容
- 最後才決定是補內容、補信任、還是先觀察

### 常見需要改善的方向
- 加強作者資訊和 E-E-A-T 信號
- 移除或改善低品質頁面
- 確保內容真正對用戶有幫助，而非只為了排名

---

### 不要做的事
- 不要 update 一來就一次改 100 個頁面
- 不要只因為焦慮就換 title、改 URL、砍大量內容
- 不要把所有問題都怪在演算法，先查技術和資料

## Coach 問法模板

當用戶說「我流量掉了」時，優先順序：

1. 「先別急，我們先排除 GSC 報表異常，再看掉的是哪些頁、哪些關鍵字。」
2. 「這個時間點有沒有剛好遇到官方更新或網站改版？」（更新日期對照 → `46-core-update-timeline.md`）
3. 「你最近有沒有改 URL、內容、robots、canonical 或主機設定？」

這樣比較像陪跑，也能避免一開口就亂猜。

## 常見修復的生效時間（給耐心卡用）

指派修復型功課時引用（完整基準 → `45-benchmarks-and-timelines.md`）：

| 修復動作 | 多久見效 | 什麼時候該懷疑有問題 |
|----------|----------|---------------------|
| 提交 sitemap | 數天～數週開始反映在 GSC | 4 週後 GSC 仍顯示「無法擷取」 |
| 移除誤設的 noindex | 數天～數週重新收錄 | 4 週後 URL 檢查仍顯示排除 |
| 改寫 title / meta | 數天～2 週反映在 SERP | 3 週後 SERP 仍顯示舊標題（檢查 Google 是否自行改寫） |
| 修 robots.txt 誤擋 | 數天～數週恢復爬取 | 2 週後 GSC 仍大量顯示遭封鎖 |
| 內容大幅改善 | 數週～數月重新評估 | 下一次 Core Update 後仍無起色 |
| 新站開始被收錄 | 無固定月份；先看重要 URL 狀態 | 重要 URL 長期未收錄 → 用 URL Inspection 查原因，不用 `site:` 數量定案 |

## 網站遷移 SEO（Site Migration）

### 遷移類型
1. 換域名（example.com → newexample.com）
2. HTTP → HTTPS
3. 換主機/伺服器
4. 換 CMS（WordPress → Shopify 等）

### 最重要的原則：一次只做一件事
同時換域名又換 CMS，出問題時很難找原因。

### 遷移 SEO 標準流程
1. 準備：備份所有數據，記錄所有 URL
2. 設定：301 重定向所有舊 URL 到對應的新 URL
3. 更新：更新 sitemap、GSC 中的域名設定
4. 驗證：抓取確認重定向正確
5. 監控：持續追蹤 4-8 週

### 邊界聲明
複雜的網站遷移（大型電商、多語系、換域名）強烈建議找有遷移經驗的 SEO 專家協助，錯誤的遷移可能造成大量流量流失。
