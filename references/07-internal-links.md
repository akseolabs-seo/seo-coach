# 內部連結（Internal Links）

## 核心概念
內部連結是網站內頁面之間的連結。它有三個核心功能：
1. **幫助爬蟲發現頁面**（沒有可爬內部連結指向的頁面，可能仍能從 sitemap 或外部連結被發現，但站內發現路徑較弱）
2. **表達頁面關係與重要性**（連結來源、上下文與錨點文字共同提供線索，不能換算成固定的「排名能量」）
3. **幫助用戶導航**（讓用戶繼續瀏覽相關內容）

**類比：** 內部連結像城市裡的道路網絡。重要頁面要有清楚、合理的路徑；孤兒頁面像沒有站內道路連接的孤島，使用者與一般網站 crawl 都無法沿站內連結到達。

---

## 連結架構原則

### 扁平化結構
重要頁面應有清楚、可爬且符合使用者任務的站內路徑。`3 clicks` 可作快篩提示，不是 Google 的排名門檻；要用實際 crawl depth、導航路徑、內鏈來源與頁面重要性判斷是否真的埋得太深。

```
好的結構：
首頁 → 分類頁 → 產品/文章頁（2-3 層）

差的結構：
首頁 → 類別 → 子類別 → 子子類別 → 文章（5 層以上）
```

### 重要頁面需要清楚的站內路徑
重要頁面應從讀者會經過、主題相關且可爬的位置取得清楚入口。不要為了增加數量而從無關頁面硬連；用實際使用者路徑、crawl 與 inbound internal link 報告驗證是否容易找到。

---

## Anchor Text（錨點文字）

### 是什麼
超連結的可見文字，例如：`<a href="/page">手工酸麵包食譜</a>` 中的「手工酸麵包食譜」。

### 重要性
Anchor text 與周圍文字能幫助讀者和搜尋引擎理解目的頁。使用描述性、符合上下文的文字即可，不要為了關鍵字而製造不自然或重複的錨點。

### 最佳實踐
- 使用描述性的文字（包含目標頁面的關鍵字）
- 自然融入句子中
- 避免「點這裡」、「更多資訊」這類沒有語義的文字

**好的：**
> 如果你想學習更多，可以參考我們的[手工酸麵包完整教學指南](/sourdough-guide/)。

**差的：**
> 想學更多？[點這裡](/sourdough-guide/)。

### Anchor Text 多樣性
不需要追求固定比例或刻意輪替錨點。讓每條連結依當下語境自然描述目的頁；檢查大量完全相同、與上下文不符的錨點是否來自模板或過度優化。

## 孤兒頁面（Orphan Pages）

### 定義
沒有任何其他頁面連結指向的頁面。爬蟲只能靠 sitemap 或外部連結才能找到它。

### 問題
- 使用者無法透過網站瀏覽找到頁面。
- 一般網站 crawl 可能看不到該頁，搜尋引擎可用的站內關係線索也較少。
- 它仍可能透過 sitemap 或外部連結被發現，因此不能只因沒有 crawl 到就斷言未索引或排名一定較差。

### 怎麼找出孤兒頁面
1. 建立 URL inventory：合併 CMS／資料庫、XML sitemap、GSC、GA4、外鏈資料與其他已知 URL 來源。
2. 從首頁執行一般網站 crawl，再用 inventory 減去 crawl 找到的 URL；差集才是孤兒頁候選。
3. 逐一驗證候選頁是否可存取、可索引，以及原始 HTML／rendered navigation 是否真的沒有 inbound internal link。

高 crawl depth 代表頁面較深，不等於孤兒頁；一般 crawler 也無法單獨證明已找出「所有」孤兒頁。

### 解決方法
在相關內容的頁面裡加入連結，或在頁尾/側邊欄加入相關頁面連結。

---

## 導航連結 vs 內容連結

### 導航連結（Navigation Links）
- 出現在選單、頁尾、麵包屑
- 每頁都有
- 適合表達全站或區段層級、支援固定導航任務

### 內容連結（Contextual Links）
- 出現在文章/頁面內文中
- 語境相關，anchor text 更有意義
- 適合在讀者需要延伸資訊或下一步時連到相關頁面

**結論：** 依頁面角色與使用者路徑選連結位置。核心導覽頁通常需要穩定導航入口；內容頁只在語境真的相關時加入 contextual link。不能只靠位置斷言某一類連結一定有較高 SEO 權重。

## 內部連結的數量

沒有按文章字數決定內鏈數量的通用公式。逐段問三件事：讀者是否需要下一步資訊、目的頁是否真正完成那個任務、連結是否放在能理解點擊理由的上下文。零條可能代表漏掉必要路徑，也可能代表這頁已完整完成任務；很多條也不一定有問題，但重複、無關或模板化連結應進一步檢查。

完成後用 rendered page 驗證連結可見、href 正確、目的頁回傳預期狀態；再從目的頁或 crawl 報告確認 inbound link 已出現。數量只記錄現況，不當成及格線。

### 三個基本原則
1. **不要關鍵字直接加連結就丟了** — 周圍文字要改寫，讓「為什麼點」自然浮現
2. **錨點要 transactional 或解釋型，不是純關鍵字塞** — 讀者得看得出點擊的理由
3. **鎖定相關舊文** — 用 sitemap 對照搜尋意圖，不是隨便挑

### 上下文必須改寫
每加一條內鏈，回頭看那個段落——**有沒有給讀者點下去的理由？** 沒有就改寫。光把關鍵字變藍色不算內鏈。

### 批次處理工具
有幾百篇文章要重整時，手動一篇篇做不切實際。可用公開的[內鏈優化助手](https://aistudio.google.com/apps/drive/1sCDjVOXOGiy8SvoYgHaOg0lEWf1_G-qh?fullscreenApplet=true)產生候選，再由人逐條確認相關性、目的頁與上下文。這個 Skill 不收錄或推導 App 的未公開指令。

### 用 coding agent 盤活舊文（不生新字）

如果用戶有兩三百篇舊文、沒排名又互相打架，先不要假設缺的是第 201 篇，也不要把問題固定歸因於結構。可先用 crawl、GSC、頁面內容與轉換資料分開驗證：是否缺少合理內鏈、是否有多頁承接同一查詢、主要頁是否缺少清楚入口，或其實是意圖、品質、技術或需求問題。

別只把標題貼 ChatGPT 分群（它只看標題用猜的）。Codex／Claude Code 這種 coding agent 能直接讀 sitemap、抓每頁的標題／小標／內文，再接進 GSC 查詢資料（每頁帶上吃到哪些字、曝光／點擊／排名），判斷就不是用猜的。讓它挑三種病：
- **蠶食候選**：多頁在 GSC 對同一查詢反覆取得曝光，還要核對意圖是否相同及主要頁是否不穩定
- **孤兒**：沒有任何頁連進去
- **主要頁訊號不清候選**：有曝光但承接不佳，或站內入口與內鏈沒有清楚指向預定主頁；低點擊本身不能證明被其他頁壓住

再讓它吐兩張表：哪頁該連哪頁＋錨文本怎麼下、該合併或 301 的清單。agent 甚至能直接動手（改內鏈檔案、走 WordPress REST API、寫 301 設定檔），改完用 diff 攤開、你滿意再 merge——前提是它碰得到你的 repo 或後台。

**紅線：301 跟刪文不能放它自己亂搞。** 動手前一定人工看三件事：這兩頁是不是回答同一個需求（一個採購、一個工程選型就不能硬併）、這頁在 GSC 還有沒有曝光／點擊／成交（有就把精華搬進主頁、絕不直接刪）、主頁接不接得住舊頁的人。301 分批做，做一批就等 Google 重爬、盯 GSC 看流量有沒有往主頁集中。agent 出草稿，拍板永遠是你。

## 教練常用切入點

- 用戶問「內部連結要怎麼設？」→ 先問：「你目前發新文時，有沒有從舊文連過去？舊文有沒有反過來連到新文？」
- 用戶有多篇服務相近但意圖可區分的內容 → 先畫讀者任務與頁面關係；hub-and-spoke 只是可選結構，不按篇數硬套
- 用戶說「我有幾百篇要重新整理」→ 工具化場景，推 AI Studio 內鏈助手，不要叫他手動一篇篇做
- 用戶寫完一篇文章不知道內鏈插哪 → 從讀者下一個合理任務找目的頁，再驗證相關性、href、HTTP 狀態與 rendered link，不用字數配額

### 行動項範本
> 「這週挑你最近發的一篇文章。先圈出一個讀者看完後真的需要的下一步，再從 sitemap 或站內搜尋找一個能完整回答的現有頁面。加入一條上下文清楚的連結後，打開真實頁面確認連結看得到、網址正確、目的頁正常回應；答不出『讀者為什麼要點』就先不要加。」
